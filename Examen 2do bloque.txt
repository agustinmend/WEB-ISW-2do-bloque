Servicio de administración de Django
-Utilizar Django 4.2 o 5.x. Django solo debe exponer el panel de administración, no API endpoints
-El schema de postgres para las tablas debe estar en un content schema(no publico). Todos los modelos deben estar en ese schema
-Utilizar claves primarias UUID para todas las tablas de dominio
-Todas las tablas deben tener campos created y modified timestamp fields
-El administrador debe admitir la búsqueda, el filtrado y la edición en linea de los recursos secundarios
-En el primer inicio, se debe crear automáticamente un superusuario con las credenciales obtenidas de las variables de entorno

FastAPI Public API
-Read-only endpoints(GET) sobre la misma base de datos postgres utilizada por Django
-Debe exponer al menos:
 -GET /api/v1/<resource>/ — Lista paginada con filtrado opcional
 -GET /api/v1/<resource>/{id} — Elemento único con todos los datos secundarios relacionados.
 -GET /api/v1/<resource>/search/?query=... — Búsqueda de texto en los campos principales.
-Todas las respuestas deben ser json utilize modelos Pydantic para los esquemas de respuesta
-El servicio FastAPI NO debe depender del servicor Django en tiempo de ejecución(solo de PostgreSQL + Redis)

Caching
- Utilice Redis para almacenar en cache las respuestas de lista y detalle
- La estrategia de invalidación de la cache es a su elección, explíquela en el archivo README.
- Los fallos de cache no deben provocar la caída de la API, si Redis no esta disponible la API debe seguir proporcionando respuestas desde PostgreSQL(degradación controlada)

Lógica de negocio OBLIGATORIO
-Implementar al menos una lógica de negocio no trivial de la siguiente lista. Elegir una que se ajuste a el dominio. La lógica debe ser ejecutada por el servicio FastAPI, no solo por el administrador
1. Control de inventario/ capacidad. Cuando la API devuelve la disponibilidad del recurso principal, el calculo debe ser correcto incluso con lecturas concurrentes(no es necesario gestionar las escrituras concurrentes, estas se gestionan a través del administrador)
2. Filtrado por intervalo de tiempo. Proporcione un endpoint que devuelva solo los elementos cuya hora de inicio se encuentre dentro de un intervalo configurable(por ejemplo, "los próximos 7 dias", "este fin de semana"). La definición del intervalo debe respetar una zona horaria que se pasa como parámetro de consulta, con UTC
3. Reglas de precios. Cada recurso principal tiene uno o mas niveles de precios con fechas de inicio y fin de validez opcionales. La API debe devolver el precio vigente para cada elemento, teniendo en cuenta la hora de la solicitud y cualquier nivel superpuesto(usted define la  regla de desempate y la documenta)
Puedes implementar mas de una solo si la primera es solida

Reverse Proxy
-Todo el trafico HTTP procedente del exterior debe pasar por Nginx en el puerto 80
-Nginx debe:
 -Enruta /admin/static/ y cualquier ruta de Django al servicio de Django
 -Enruta /api/ al servicio FastAPI.
 -Sirve los archivos estáticos de Django directamente(no redirijas las solicitudes de recursos estáticos a Django/uWSGI)
 -Oculta la versión de Nginx en los encabezados de respuesta
 -Establece tiempos de espera razonables
 -Enruta / para servir el frontend
 -Gestiona las respuestas 404 usando un HTML genérico

Application Server
- Django debe ejecutarse detrás de un servidor de nivel de producción. uWSGI o Gunicorn: usted elige
- FastAPI debe ejecitarse detrás de los procesos de Uvicorn(si lo prefiere, puede usar Gunicorn como administrador de procesos)
- El servidor de desarrollo de Django (runserver) y uvicorn --reload no son aceptables para la entrega final

Docker Compose
- Un solo comando 'docker compose up' desde la raíz del repositorio debe iniciar toda la pila: PostgreSQL, Redis, Django, FastAPI y Nginx. Después de aproximadamente 30 segundos, debería funcionar lo siguiente desde el host:
 -http://localhost/admin/ — Inicio de sesión de administrador de Django
 -http://localhost/api/v1/<resource>/ — Listado de FastAPI.
 -http://localhost/api/openapi.json — FastAPI OpenAPI schema.
 -http://localhost/ — Frontend
 -http://localhost/apiaaaaaa — 404 html page
 -A /healthz endpoint en cada servicio que verifica sus dependencias y devuelve 200/503.
-Se requieren Healthchecks

Requerimientos no funcionales

-Migraciones. Las migraciones de Django deben ejecutarse automáticamente al iniciar el contenedor. No se debe realizar un volcado SQL
-Logging. Both services must log to stdout in a parseable format.
-Test. Al menos 5 pruebas significativas por servicio. Utilice pytest
-README. Debe incluir como ejecutarlo, como probarlo, tus decisiones de diseño, las concesiones que hiciste y al menos una cosa que hariasa diferente si tuvieras mas tiempo. Añade diagramas de los sistemas. Como interactúan los modulos

Calidad del código Principios SOLID(OBLIGATORIO)
- Cada capa del código __ Django models/admin, FastAPI routers/services/reopsitories, business logic, cache layer __ debe diseñarse siguiendo los principios SOLID y los patrones de diseño. Sebuscara evidencia de los 5 durante la revisión del código. El revisor espera encontrar como mínimo:
 -Al menos una clase abstracta o protocolo por cada funcionalidad(cache, repositorio, búsqueda). Las clases concretas lo implementan
 -Constructor injection(o FastAPI Depends) en lugar de importaciones dentro de los cuerpos de las funciones
 -No se permite lógica de negocio dentro de las vistas de Django ni en FastAPI route handlers __ esta lógica se traslada a la capa de servicio
 -No se permite la concatenación de cadenas SQL dentro de las clases de servicio, esta función corresponde a los repositorios
-Una contribución que "funciona" pero consiste en un archivo views.py de 800 líneas se limitara al 60% independientemente de la exhaustividad de sus funcionalidades. Lo mismo ocurre con el código que simplemente esta ahí, pero que no aporta nungun valor a la implementación, siempre pregúntate: por que necesitamos este fragmento de código?
